## The one-line version

IntelliJ IDEA is built so you **ask for things by name** instead of hunting for them. Learn the one popup that does that, and the rest of the IDE is a set of shortcuts to things you could have asked for anyway.

Analogy: the parts counter at a dealership. You don't wander the warehouse looking for a caliper bracket; you walk up to the counter, say "front caliper bracket, 2015 Camry", and someone fetches it. Search Everywhere is the counter. Every tip below is either a faster way to say what you want at the counter, or a way to skip the counter for the handful of parts you ask for ten times a day.

Two conventions on this page:

- Shortcuts are the **default keymaps** JetBrains documents for Windows/Linux and macOS. They differ, and both are given side by side. If you've switched keymaps (or your Mac steals a combination, see [Common mistakes](#common-mistakes)), Find Action shows you the live binding.
- Menu paths are written `Parent → Child`. JetBrains writes them `Parent | Child`.

Nothing on this page has been exercised in the IDE yet. The shortcuts come from JetBrains' keymap references and reference card, not from a keyboard, and the page stays `draft` until they have been. Each table carries its own `TODO(test)` so the gap is visible.
:::

## Search Everywhere and Find Action: the one entry point

**What it is.** One popup that searches your classes, files, and symbols, plus IDE actions, settings, UI elements, and Git branches and commits. It's tabbed (Classes, Files, Symbols, Actions, Text, and optional tabs such as Git), and each tab also has its own direct shortcut.

**Why it saves time.** You stop needing to know where anything lives. Can't remember whether "line separator" is under Editor or Code Style? Type it. Want the Git branch popup? Type it. And because **Find Action** lists the shortcut next to every action it finds, you learn the shortcuts for the things you actually use, in the order you use them, rather than from a poster. Select an action in that list and press the intention-actions shortcut to assign it a shortcut on the spot.

**How to use it well.**

- Type `/` to jump straight to a settings group: `/plugins`, `/appearance`, `/inspections`, `/templates`, `/vcs`, `/registry`.
- Press the Search Everywhere shortcut a second time (or `Alt+N` on Windows) to include non-project items such as library classes.
- File search accepts CamelCase and snake_case abbreviations, so `UsRepImpl` finds `UserRepoImpl`.
- It also evaluates basic arithmetic and functions like `sqrt()`, which is handy more often than it sounds.

## Getting around: recent files and navigation

**What it is.** A family of jumps that follow the *meaning* of the code rather than the text: to a declaration, to its implementations, to the type of a variable, to the method this one overrides, and back along the trail you took to get there.

**Why it saves time.** In a Spring Boot codebase you spend more time reading than typing. Reading with the mouse means scrolling and re-finding your place. Reading with these jumps means the IDE keeps the trail: Go to Declaration follows a call, Back returns you, Recent Files reopens the four files you were juggling, and Last Edit Location takes you to the line you were actually changing before you went exploring.

**How to use it well.** Treat Back/Forward like browser history and dive freely. Use Recent Files over the editor tabs; it's faster than finding a tab and it works with tabs closed. Go to Declaration on a symbol you're already standing on shows its usages instead, so one key does both directions.

## Alt+Enter: intention actions and quick fixes

**What it is.** The IDE constantly analyses the code under the caret. When it has something to offer it shows a bulb: a **yellow bulb** is an *intention action* (an improvement it can make, such as converting a loop or adding a `final`), a **red bulb with an exclamation mark** is a *quick-fix* for a problem it detected. Together JetBrains calls them *context actions*, and one shortcut lists all of them.

**Why it saves time.** It is the fastest way to fix a red underline, add a missing import, create a method that doesn't exist yet from its call site, or flip an `if` around. It's also the door to things that aren't fixes at all: put the caret on a `main` method and the same menu offers *Modify Run Configuration*.

**How to use it well.** Press it on anything red first, before you go reading. Press it on anything that *feels* clumsy second; the yellow bulb usually has an idea. You can switch individual intentions off in Settings → Editor → Intentions if one keeps nagging you, and hide the bulb entirely in Settings → Editor → General → Appearance ("Show intention bulb").

| --- | --- | --- |
| Show Context Actions (intentions and quick fixes) | Alt+Enter | ⌥ ⏎ |
| Complete Current Statement (close the brackets, add the `;`, move on) | Ctrl+Shift+Enter | ⌘ ⇧ ⏎ |
| Parameter Info (which argument am I on?) | Ctrl+P | ⌘ P |

## Refactoring

**What it is.** Structural edits the IDE performs *with knowledge of the code*: rename a class and every reference, import, and file name follows; pull a block of lines into a new method and the parameters and return value are worked out for you; inline a variable and its expression is substituted everywhere. JetBrains describes refactoring as improving code without adding functionality.

**Why it saves time.** The alternative is find-and-replace and hoping. The IDE knows that `save` in `UserService` and `save` in `OrderService` are different methods, and that the string `"save"` in a log message isn't a method at all. It shows a preview of affected usages in the Find tool window when the change is wide, warns about conflicts, and a single undo reverts the whole thing.

**How to use it well.** If you don't know which refactoring you want, press **Refactor This** and read the list for the thing under the caret. The three you'll use most in a service class are Rename, Extract Method, and Introduce Variable. Extract Constant is how a magic number becomes `private static final` with one keystroke.

## Code completion: basic, smart, postfix

**What it is.** Completion pops up as you type and lists what could go here. There are two flavours worth telling apart, plus a third trick that works backwards.

| | Basic completion | Smart (type-matching) completion |
| --- | --- | --- |
| Shortcut (Windows / macOS) | Ctrl+Space / ⌃ Space | Ctrl+Shift+Space / ⌃ ⇧ Space |
| What it lists | Names of classes, methods, fields, and keywords reachable from the caret | Only the suggestions whose **type fits** what the code expects at the caret |
| Best moment | Almost always; it also pops up on its own as you type | On the right-hand side of an assignment, inside a method call's parentheses, after `return`: anywhere the type is already decided |
| Also includes | Live templates (see below) | |

**Why it saves time.** Basic completion saves typing. Smart completion saves *thinking*: when a method wants a `Duration`, smart completion won't offer you a `String`, so a short list is a correct list.

**Postfix completion** works backwards. Type an expression first, then a dot and a short template such as `.var` or `.sout`, and the IDE wraps or rewrites the expression: `userRepo.findAll().var` becomes a local variable declaration, `result.sout` becomes a print statement. JetBrains' own tip is to type `.` and press Up in the suggestion list; the postfix templates are collected at the bottom. The full list, and which key expands them (Tab, Enter, or Space), lives in Settings → Editor → General → Postfix Completion.

Also on the completion menu: ML-assisted ranking, which reorders suggestions by how likely you are to pick them, and Full Line completion, which proposes whole lines.

## Live templates

**What it is.** Abbreviations that expand into a block of code with fill-in-the-blank fields. Type the abbreviation, press **Tab**, then keep pressing Tab to hop between the fields (Shift+Tab goes back).

**Why it saves time.** `psvm` + Tab is a `main` method; `sout` + Tab is `System.out.println();` with the caret inside the parentheses. Small, but you type them dozens of times a week, and every template you write yourself (Settings → Editor → Live Templates) pays back the same way. For this site's owner the obvious custom ones are a Lombok-annotated DTO shell and a `@RestController` skeleton.

Templates JetBrains documents for Java:

| `psvm` or `main` | `public static void main(String[] args) { }` |
| `sout` | `System.out.println();` |

| `fori` | A `for` loop over an index (JetBrains Guide) |
| `iter` | An iteration loop (JetBrains Guide) |
| `ifn` | `if (var == null) { }` |
| `nn` | A not-null check (JetBrains Guide) |
| `psfs` | `public static final String` |

## Run/debug configurations and the debugger

**What it is.** A run/debug configuration is a named set of startup properties: what to run, with which arguments, environment, and working directory. Running a class without one makes a *temporary* configuration (the IDE keeps at most five by default, set under Settings → Advanced Settings → Run/Debug); saving it makes it *permanent*. Permanent configurations can be stored as project files, which land in `.idea/runConfigurations` and can be committed so the whole team runs the app the same way.

**Why it saves time.** One key runs the app the same way every time, with the same `SPRING_PROFILES_ACTIVE`, instead of re-typing a Maven command. And a debugger session is the same configuration started with breakpoints armed, so there's nothing extra to set up.

**How to use it well.** Make the configuration permanent as soon as you've run the app once (Run widget → Save Configuration, or put the caret on `main` and use the context actions menu → Modify Run Configuration). Tick "Store as project file" if teammates should share it, and let `.idea/runConfigurations` through your `.gitignore` while still ignoring the rest of `.idea`.

### The debugger in five moves

A **breakpoint** is a marker where the debugger freezes the program so you can look around. Click the gutter next to a line to set one, or use the shortcut. Right-click it for a *conditional* breakpoint (only stop when `order.getTotal() > 1000`) or a *logging* breakpoint that prints an expression and keeps going; Shift+click the gutter sets a logging one directly. Besides line breakpoints there are method breakpoints, exception breakpoints (stop wherever a given `Throwable` is thrown, even in library code), and field watchpoints (stop when a field is read or written).

Once stopped, the Debug tool window shows **Frames** (the call stack; click one to see its variables), **Variables**, and **Watches** (expressions you pin to re-evaluate after each step). Variable values also appear inline in the editor.

Stepping, in the words that matter:

- **Step Over** runs the current line and stops on the next one, *even if the line calls methods*. Use this to walk through your own method.
- **Step Into** enters the method call on the current line. Use this when the bug is inside what's being called. **Smart Step Into** lets you pick which call on a line with several.
- **Step Out** finishes the current method and stops back in the caller.
- **Run to Cursor** keeps going until it reaches the line you're on. Faster than adding and removing a breakpoint.
- **Evaluate Expression** runs any expression against the live program state: call a getter, check a map, even mutate a field. Quick Evaluate does the same for the selected text.

| --- | --- | --- |
| Toggle Line Breakpoint | Ctrl+F8 | ⌘ F8 |
| View Breakpoints (the dialog) | Ctrl+Shift+F8 | ⌘ ⇧ F8 |
| Step Over | F8 | F8 |
| Step Into | F7 | F7 |
| Smart Step Into | Shift+F7 | ⇧ F7 |

## Maven and Gradle: the tool window and syncing

**What it is.** IntelliJ IDEA doesn't read your `pom.xml` or `build.gradle` live. It *syncs* from them into its own project model, and it's that model which drives completion, navigation, and the red underlines. The **Maven tool window** (View → Tool Windows → Maven) shows each project's Lifecycle phases, Plugins, Dependencies, Profiles, and Repositories, with a toolbar for running goals, toggling offline mode, skipping tests, and reloading. Gradle has an equivalent window.

**Why it matters.** The single most common "IntelliJ is broken" report in a Spring Boot project is: someone added a starter to `pom.xml`, the imports stay red, and they start reinstalling things. The project simply hasn't been synced. Every time you edit the build file by hand, a sync icon appears at the top-right of the editor; click it, or use the shortcut.

**How to use it well.**

- After a hand edit to `pom.xml`: **Sync Maven Changes** (the editor icon, `Ctrl+Shift+O` on Windows/Linux). For Gradle it's **Sync Gradle Changes**, same shortcut.
- From the tool window: **Sync All Maven Projects** is incremental; **Reload All Maven Projects** is the full rebuild of the model. Reach for the full reload when the incremental one leaves something red. Gradle's equivalent is **Sync All Gradle Projects**.
- To stop thinking about it: Settings → Build, Execution, Deployment → Build Tools → "Sync project after changes in the build scripts", set to *Any changes* (or *External changes* to sync only after a `git pull`).
- Maven's own settings (which Maven to use, user settings file, offline mode) are under Build, Execution, Deployment → Build Tools → Maven; Gradle's under Build, Execution, Deployment → Gradle, where "Build and run using" chooses whether the IDE or Gradle compiles and runs your code.
- Set the **project JDK** under File → Project Structure → Project. If nothing's installed, *Download JDK* fetches one from Oracle OpenJDK, Adoptium, or Amazon Corretto. The runtime bundled with the IDE only runs the IDE; it has no compiler, so you still need a real JDK for Java work.

## Git integration and Local History

**What it is.** Git is built in: VCS → Enable Version Control Integration turns it on for an existing folder, VCS → Create Git Repository initialises one, and File → New → Project from Version Control clones. The **Commit tool window** lists your local changes grouped into *changelists* (there's one called *Changes* by default; you can make more and move files between them to commit related edits separately). The **Git tool window** holds the Log. The current branch sits in the window header's VCS widget.

**Why it saves time.** Commit checks. In the Commit tool window's options you can have the IDE reformat code, optimise imports, analyse the changed files, and run a test configuration *as part of every commit*, so a sloppy commit never leaves your machine. Amend, Commit and Push, and the push dialog (with per-repository target branches) are all there without a terminal. If you prefer Git's real staging area over changelists, turn it on under Settings → Version Control → Git → "Enable staging area".

**Local History** is the safety net under all of it. The IDE silently records every change to project files, including ones made outside the IDE, whether or not Git is enabled, and keeps them for five working days by default (Settings → Advanced Settings → IDE, or the `localHistory.daysToKeep` property). Right-click a file or folder → Local History → Show History to see and revert; File → Local History → Put Label marks a state you may want back, say before a large refactoring. It is not a backup: it's local, it expires, and Invalidate Caches can wipe it if you tick the wrong box.

## Settings: sync, share, and the keymap

**Backup and Sync** (a bundled plugin, formerly Settings Sync) stores your settings against your JetBrains Account and applies them to every IDE you sign into: UI settings (theme, fonts, colour scheme, toolbars), code settings (code style, live templates, editor options, inlay hints, intentions), tool settings (version control, debugger, database), system settings, and the enabled/disabled state of plugins. Enable it under Settings → Backup and Sync.

**Export / Import** is the file-based route: File → Manage IDE Settings → Export Settings writes a ZIP you can carry to another machine or check into a dotfiles repo; Import Settings… reads one. It covers a little more than sync does (deployment servers, Git accounts, registry keys).

**Restore Default Settings** (same menu) resets the IDE and, importantly, backs up the current configuration first to `%APPDATA%\JetBrains\<product><version>-backup` on Windows or `~/Library/Application Support/JetBrains/<product><version>-backup` on macOS.

**Keymap** lives under Settings → Keymap. Predefined choices include *Windows* (the default there), *macOS* (the default there), *IntelliJ IDEA Classic* (Windows-style shortcuts on a Mac), *macOS System Shortcuts* (avoids collisions with the OS), and Eclipse/NetBeans layouts for people who came from those. To rebind: find the action, right-click, Add Keyboard Shortcut. To undo a rebind: right-click → Reset Shortcuts. Custom keymaps are files under `%APPDATA%\JetBrains\<product><version>\keymaps` (Windows) or `~/Library/Application Support/JetBrains/<product><version>/keymaps` (macOS), so they can be backed up too.

**Actions on Save** (Tools → Actions on Save) can reformat code and optimise imports every time you save, which makes the commit checks above mostly redundant on your own machine.

## Plugins

Settings → Plugins has three things: the **Marketplace** tab (JetBrains Marketplace, searchable with filters such as `/tag:AI`), the **Installed** tab, and a gear menu with *Install Plugin from Disk* (a ZIP or JAR you downloaded yourself), *Update Plugins Automatically*, and *Disable all downloaded plugins*. Plugins that ship with the IDE are *bundled*: you can disable them but not uninstall them, and disabling ones you don't use is a legitimate way to make the IDE lighter.

Two features worth knowing for a team:

- **Required Plugins** (Settings → Appearance & Behavior → Required Plugins) records that this project needs plugin X between versions A and B in `.idea/externalDependencies.xml`, so a teammate who opens the project without it gets told.
- Plugins can be installed from the command line for scripted setups: `idea64.exe installPlugins <PluginID>` on Windows.

The one plugin every beginner should install is **Key Promoter X**: each time you click something with the mouse it pops up the shortcut you could have pressed, and it keeps a tally of the ones you keep missing.

## Community vs Ultimate

:::caution
The editions changed in late 2025. IntelliJ IDEA 2025.1 (installed on this machine) still ships as two products; from 2025.3 there is one installer. Both are described below; check which you're on before trusting a feature list you read elsewhere.
:::

**Up to 2025.2**, JetBrains' installation guide described two editions:

| | Community Edition | Ultimate |
| --- | --- | --- |
| Licence | Free and open source, Apache 2.0 | Commercial, with a 30-day trial |
| Scope | "all the basic features for JVM and Android development" | Community plus "additional tools and features for web and enterprise development" |

**From 2025.3**, there is a single product called IntelliJ IDEA. Its core stays free (and, per JetBrains, with more in it than the old Community Edition had), and an **Ultimate subscription** unlocks the rest; a 30-day Ultimate trial starts on install and you drop back to the free tier afterwards. The open-source code stays on GitHub. JetBrains' plan lists these splits:

| Capability | Free tier | Ultimate subscription |
| --- | --- | --- |
| Java, Kotlin, Groovy, Scala, Maven/Gradle projects, Git, run and debug | Yes | Yes |
| **Spring** and Spring Boot | Syntax highlighting and the project wizard only; JetBrains says Spring support is "limited" without Ultimate | Full support: bean navigation, context actions, embedded docs, Spring run configurations and endpoints |
| Jakarta EE, JPA, Thymeleaf, FreeMarker, Velocity, Kubernetes, Helm | Syntax highlighting and project wizards | Full support |
| Quarkus, Micronaut, JSP, JavaScript/TypeScript and other non-JVM languages | Not in 2025.3; JetBrains says they are planned for the free tier in later releases | Yes |
| Database tools | Browse schemas (tables, columns, indexes) without querying data | Full database tools |
| HTTP Client, profiler, diagrams, remote development, AI Assistant | No | Yes |

**What that means for this site's owner:** everything in the Spring Boot backend recipe can be *built* on the free tier, because Maven, Java, Lombok annotation processing, JDBC, and Git are all core. What Ultimate adds is the Spring-aware layer: jumping from an `@Autowired` field to the bean that satisfies it, seeing your `@GetMapping` endpoints listed, and Spring Boot run configurations with profile and actuator support. If you write Spring all day, that layer is the reason to pay; if you're learning, the free tier plus the plain Application run configuration is enough to get through every level here.

## Common mistakes

- **Doing everything with the mouse.** The IDE is designed around the keyboard. Install Key Promoter X for a week and let it nag you, and use Find Action for anything you can't remember.
- **Editing `pom.xml` and not syncing.** Red imports after adding a dependency are almost never a broken install. Click the sync icon or press the shortcut; if it's still red, Reload All Maven Projects.
- **On a Mac, wondering why two shortcuts do nothing.** macOS claims `⌃ Space` (switch input source) and `⇧ ⌘ A` (Terminal's man-page search) for itself; JetBrains lists both as known conflicts. Change the OS binding or pick the *macOS System Shortcuts* keymap.
- **Expecting full Spring tooling on the free tier.** You'll get highlighting and a wizard. Bean navigation and Spring run configurations are Ultimate.
- **Reaching for Invalidate Caches first.** Try File → Cache Recovery → Repair IDE, which fixes one project step by step without restarting; Invalidate Caches wipes every project's caches and restarts. And read the checkboxes: "Clear file system cache and Local History" throws away your safety net.
- **Treating Local History as a backup.** Five working days, local only, and gone when the IDE's caches are cleared. Commit.
- **Losing a run configuration.** Temporary configurations are capped at five; the sixth pushes the oldest out. Save the ones you care about.
- **Committing all of `.idea` or none of it.** Share `.idea/runConfigurations` (with "Store as project file") and Required Plugins; ignore the rest.
- **No project SDK.** Nothing compiles until File → Project Structure → Project points at a real JDK. The IDE's bundled runtime isn't one.
